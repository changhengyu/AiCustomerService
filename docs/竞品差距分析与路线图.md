# 竞品差距分析与改进路线图

> 对标对象：Intercom / Zendesk Suite / Salesforce Service Cloud / HubSpot Service / 美洽 / 智齿 / Udesk / 网易七鱼 / 容联七陌
> 评估时间：2026-06-26
> 当前代码版本：v0.4.0
> 评估方法：通读 backend 4 个项目源码 + admin/miniprogram 全部页面 + 与上述竞品公开功能矩阵逐项比对

---

## 1. 总体结论（一句话）

**当前系统在"AI 客服 SaaS"这条赛道完成了最小可行产品（MVP）的 60–65%**——对话引擎、多渠道接入、多租户、计费框架、可观测性已经齐备，但**和美洽/Udesk/智齿这种成熟 SaaS 相比，缺的是让"客户成功团队愿意付费"的那一层**：实时性、工单流、可视化运营后台、质检与 SLA、移动端完整性、文档与开发者生态。

如果只挑 3 个最关键差距：**① 实时推送（SignalR / WebSocket）缺位 → ② 没有工单与 SLA 模块 → ③ BI 报表只在后端接口里写了一次，前端没图表组件**。

## 2. 差距清单（按"做什么 / 怎么做 / 参考 / 工作量"格式）

### 2.1 实时通信（P0，最高优先级）

| 维度 | 现状 | 行业基线 | 差距 |
| --- | --- | --- | --- |
| 客服工作台新消息提醒 | 轮询 `onMounted` / `onShow` 重拉 | 浏览器/APP 内推送 + 角标 + 声音 | 无实时，**最差体验点** |
| AI 打字状态 | 模板里有 `aiTyping` 标志但**从未被置为 true** | 流式输出 + 真实打字机效果 | 死代码 |
| 客服在线状态/分配通知 | 无 | Intercom Presence / Zendesk Agent Status | 无 |
| SLA 倒计时 | 无 | 实时倒计时 + 溢出告警 | 无 |

**做什么**：在 `.NET 10` 侧引入 **SignalR**（native AOT 友好），前端 admin 用 `@microsoft/signalr`，uni-app 用 `uni.connectSocket`（小程序/H5 不一致，封装抽象层）。

**怎么做**：
1. 新建 `AiCustomerService.Api/Hubs/WorkbenchHub.cs`，注册 `/hubs/workbench`
2. Hub 方法：`NewMessage(conversationId)` / `AgentAssigned` / `Typing` / `SlaWarning`
3. 服务端在 `ConversationService.AppendAgentMessageAsync`、`Hangfire` 的 `WebhookDispatchJob` 完成时广播
4. 客户端封装 `realtime.ts`（admin）和 `realtime.ts`（uni-app，平台分流 WebSocket）
5. JWT 鉴权握手：SignalR `OnConnectedAsync` 解析 QueryString 中的 access_token

**参考**：
- ASP.NET Core SignalR 官方文档：<https://learn.microsoft.com/aspnet/core/signalr/>
- Microsoft.Extensions.AI 流式输出与 SignalR 集成 demo：<https://github.com/dotnet/ai-samples>
- Zendesk Talk / Intercom Inbox 的实时架构白皮书

**工作量**：后端 3–5 天 + 前端 3 天 + 联调 2 天 = **8–10 人天**。

### 2.2 工单系统（P0）

| 维度 | 现状 | 行业基线 |
| --- | --- | --- |
| 工单实体 | 无 | 美洽/Udesk/Zendesk 标配 |
| SLA 策略 | 无 | Zendesk SLA 99% 8h 之类的策略编辑器 |
| 内部备注 / @ 同事 | 无 | Zendesk 内 note 与 public reply 分开 |
| 宏 / 快捷回复 | 无 | 美洽快捷回复、Zendesk Macros |
| 工单状态机 | 无 | new → open → pending → hold → solved |
| 工单转人工触发 | 现在用关键词 | 通过工单模板自动转 |

**做什么**：新建 `Ticket` / `TicketComment` / `TicketMacro` / `SlaPolicy` 4 个实体 + `TicketService` / `SlaService` / `MacroService` 3 个 service + `TicketController` / `SlaController` / `MacroController` 3 个 controller。

**怎么做**：
1. 实体设计参考 Zendesk Tickets API（公开 schema 文档齐全）：
   - `Ticket { Id, TenantId, RequesterId, AssigneeId, Subject, Status, Priority, Channel, CreatedAt, FirstReplyAt, SolvedAt }`
   - `TicketComment { Id, TicketId, AuthorId, Body, IsPublic, CreatedAt }`
   - `SlaPolicy { Id, TenantId, Name, FirstReplyMinutes, NextReplyMinutes, Conditions }`
2. 触发器：关键词转人工时自动开 ticket；客户在历史会话里也可由客服手动开
3. SLA：Hangfire `RecurringJob` 每分钟扫描 `SlaService.EvaluateAsync()`，生成事件 `sla.breached`
4. 前端 admin 新增 `/tickets` 列表 + `/tickets/:id` 详情 + `/settings/sla` 配置页

**参考**：
- Zendesk Support API：<https://developer.zendesk.com/api-reference/ticketing/tickets/tickets/>
- 美洽工单模块产品文档
- osTicket（开源工单系统）：<https://osticket.com/>

**工作量**：实体 + 服务 + API = **10 人天**；前端列表/详情 = **5 人天**；SLA 引擎 = **3 人天**。合计 **18 人天**。

## 6. 风险点与注意事项

1. **Hangfire 在 API 进程内**：与 API 共享生命周期 → 重启即丢任务（其实 Hangfire 持久化了，但内存中的 worker 状态会丢）。v0.6 应该把 Hangfire 拆到独立服务（真正启用 Worker 项目）。
2. **微信支付的"简化"实现**：当前版本生产部署可能因为签名失败导致回调被拒，v0.5 必须先修。
3. **占位 STT `NoopSttProvider`**：未配置阿里云 Key 时直接返回固定字符串（"语音消息功能未配置"），正式上线前要替换或强制要求配 Key。
4. **`pages/customer/index` 死路由**：uni-app pages.json 引用但文件不存在，编译警告但能跑——v0.5 直接补上。
5. **后端无单元测试**：所有重构都建立在沙子上，任何一个公共方法都不能保证不回退。
6. **`BiService.cs:110` 的"高频问题"是按 `message.content` 词频聚合**：当前实现就是字符串切词+count，没做任何去噪（"你好""谢谢"会被算进来），上线前要改。
7. **i18n 在 uni-app 中"非响应式"**：切换语言不会自动重渲页面，需要 `localeChange` 事件总线改造。
